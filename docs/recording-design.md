# 学習記録の作成設計

## 対象と保存規則

本人がログインし「記録する」を押すとモーダルを開く。既存のStudy Logに新しいページを1件だけ作成する。既存記録の更新・削除、週目標への書き込み、任意のNotionページへの書き込みは実装しない。

|項目|規則|
|---|---|
|勉強内容|必須、前後の空白を除き1〜160文字。プレーンテキスト|
|教科|必須。取得時・保存時に実スキーマのselect選択肢を確認し、保存には既存option IDを使う|
|終了日時|日本時間。オフセット付きISO日時に正規化。2000年以降、未来5分までの時計ずれを許容|
|実績時間|1〜1440分の整数。計画時間は受け付けない|
|単元|任意、200文字以内。Notionに項目が存在する場合だけ表示・保存|

終了日時はNotionの「日付」の単一の日時として保存。終了日や作成日時へ置き換えない。終了日時から実績分だけ逆算した推定時間帯を保存前に表示し、休憩は判別できない旨を明記。日付・時刻・時間を実記録から勝手に補完しない。

## APIと権限

- GET /api/records：本人認証後に有効化状態・教科選択肢・単元の有無を返す。プロパティIDやトークンは送らない。
- POST /api/records：サーバーで本人のメール許可リスト、Origin、Sec-Fetch-Site、Content-Type、8KBの本文上限、入力値、既存選択肢を確認。
- データソースIDや任意のプロパティをリクエストから受け付けない。Notion SDKはサーバーだけで使う。
- NOTION_WRITE_ENABLED=true が必要。NOTION_WRITE_TOKENを指定した場合は保存用に使用し、未指定ならNOTION_TOKENを使用。
- Notion側はRead/Insert contentのみ。Update/Deleteは不要。単一の既存接続を使う場合、Insert権限はその接続に共有された週目標にも技術的に及ぶ。アプリの保存先はStudy Logに固定する。接続レベルでも分離したい場合はStudy Logだけに共有した別の保存用接続とNOTION_WRITE_TOKENを使う。

## 二重保存と障害

- ブラウザの送信中フラグ・ボタン無効化、サーバーの共有ロック、全端末共通10秒間隔を組み合わせる。
- UUIDのIdempotency-Keyと正規化した入力のハッシュをRedis/永続Storeに最大7日保存。作成前にpendingを確定し、完了後にNotionページID/URLを記録する。保存済みの同一IDは元の結果を返す。内容の差し替えは409。
- 作成POSTはSDKの自動リトライを無効にする。429はRetry-After以前の新しい作成を抑止する。
- 400/401/403/404/429は作成されなかった応答として扱い、同じIDでの再操作を許す。5xx、タイムアウト、作成後の結果保存失敗、pendingのままの停止は未確定とする。
- 未確定の場合は入力と再送を止め、Notionを確認する導線を出す。Notion APIに冪等性保証がないため、通信の不確実性を隠して「絶対に一度だけ保存」とは保証しない。7日後・別ID・再読み込み後の手動再入力まで重複排除する仕組みではない。
- 成功時は同期キャッシュを無効化し、再取得する。無効化できなかった場合も作成自体を失敗と表示せず、更新保留を知らせる。
- デモは架空データにのみ追加し、NotionへのPOSTを行わない。

## 操作と検証

ネイティブdialogでフォーカスを閉じ込め、Escと閉じるボタンを提供する。送信中は閉じられず、通常の閉じる操作では下書きを維持。成功後はNotionへのリンクを表示する。

入力境界、認証・送信元・サイズ制限、同時送信、同一ID再送、結果不明時の再送停止、429の待機、PC/スマホでのプレビュー・デモ保存を検証。実データを使った本番書き込みは本人が保存する最初の記録で確認し、架空の記録を本番に作成しない。
